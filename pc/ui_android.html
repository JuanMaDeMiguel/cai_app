Rediseño de la UI Android

1 · Punto de partida

La app tiene un único propósito: leer el sensor de luz ambiente del teléfono, convertirlo a un porcentaje de brillo y enviarlo por Bluetooth a la PC. Es una utilidad, no una app de contenido. Eso condiciona el diseño: claridad por encima de adornos.

Antes y después

La versión original era un ConstraintLayout con cuatro TextView, un Button y un Switch apilados contra el borde superior izquierdo, sin jerarquía visual ni color. Funcionaba, pero "se veía como el editor de Android Studio recién creado".

El rediseño mantiene exactamente la misma funcionalidad y reorganiza la información en torno al dato importante (el porcentaje), con una tarjeta destacada, una paleta Material 3 y soporte de modo oscuro.

AntesDespués

El % con el mismo peso que todoEl % destacado en una tarjeta

Filosofía del rediseño

  • Sobrio y elegante. Un único color de acento, mucho espacio en blanco, esquinas redondeadas. Nada de gradientes ni animaciones.
  • Material Design. Usamos el tema Theme.Material3.DayNight y sus tokens de color, como recomienda la práctica moderna de Android.
  • Que parezca hecho a mano. Recursos separados (colores, strings, drawables) y referencias por atributo de tema — justo el flujo que enseña la cátedra PDF · p.33-36.
  • Backend intacto. Ni una línea de lógica modificada. Esto es una restricción, no un lujo, y dirige varias decisiones (ver §3).

2 · Fundamentos de la cátedra que usamos

Antes del código conviene fijar el vocabulario del PDF, porque todo el rediseño es una aplicación directa de estos conceptos.

View y ViewGroup PDF · p.28-29

La cátedra introduce la jerarquía base de la interfaz gráfica:

                 ┌─────────────┐
                 │    View     │   ← unidad mínima dibujable
                 └──────┬──────┘
            ┌───────────┴───────────┐
      ┌─────┴──────┐          ┌──────┴──────┐
      │ ViewGroup  │          │   Widget    │
      │ (Layout)   │          │ (Button…)   │
      └─────┬──────┘          └─────────────┘
            │ contiene Views
            ▼
   LinearLayout · RelativeLayout · ListView · ...
  • Una View es cualquier elemento dibujable (un texto, un botón).
  • Un ViewGroup es una View que contiene otras Views: es un layout. La p.29 lista los tipos: LinearLayout, RelativeLayout, ListView, GridView…

En el rediseño anidamos ViewGroups: un ConstraintLayout raíz, dentro un LinearLayout vertical, y dentro tarjetas (MaterialCardView, que también es un ViewGroup) con más LinearLayout. Esa composición "cajas dentro de cajas" es exactamente el modelo de la diapositiva.

Widgets PDF · p.31

La p.31 muestra el catálogo de widgets: Button, TextField, slider, checkbox, radio, switch… Nuestra pantalla usa tres familias: TextView (mostrar datos), Button (acción conectar) y Switch (envío automático). El ImageView de los iconos también es un widget.

Declaración XML del layout PDF · p.32

La cátedra contrapone dos formas de construir la UI:

  1. Por código Java PDF · p.30: new LinearLayout(this), l.addView(t), setContentView(l).
  2. Declarativa en XML PDF · p.32: se describe el árbol en un .xml y en la Activity se hace setContentView(R.layout.main).

Usamos la forma declarativa (la recomendada): toda la pantalla vive en res/layout/activity_main.xml y MainActivity solo hace setContentView(R.layout.activity_main). Comparen el esqueleto del slide con nuestro archivo: es el mismo patrón <LinearLayout orientation="vertical"> con hijos dentro.

R.java y recursos PDF · p.33-36

Este es el corazón teórico del rediseño. La cátedra explica:

  • p.33 Todo lo que ponés en /res genera entradas en R.java (que no se toca a mano). Por eso podemos escribir R.layout.activity_main, R.id.brightnessText, R.drawable.ic_bluetooth.
  • p.34-35 Tipos de recurso por carpeta: values-[qualifier]/ (textos, estilos, dimensiones), color/, drawable-[qualifier]/, layout-[qualifier]/. El qualifier es lo que hace que values-night/ sea el modo oscuro.
  • p.36 "Exploiter les ressources": referenciar un recurso desde otro con "@color/..." o "@string/...", e incluso recursos del sistema con "@android:color/...".

El rediseño es, esencialmente, poner en práctica la p.36: en lugar de cablear android:text="Conectar" y colores en hexadecimal dentro del layout, definimos los recursos una vez y los referenciamos. Eso es lo que lo hace mantenible y traducible.

3 · La restricción clave: no tocar el backend

El "contrato" findViewById

La Activity y el layout están unidos por los id. En Java se hace:

MainActivity.java java
private TextView luxText, brightnessText, statusText;
private Button connectButton;
private Switch sendSwitch;
// ...
brightnessText = findViewById(R.id.brightnessText);
connectButton  = findViewById(R.id.connectButton);
sendSwitch     = findViewById(R.id.sendSwitch);

findViewById busca en el árbol del layout una View con ese id y la castea al tipo de la variable. De ahí salen dos reglas que el rediseño respeta a rajatabla:

  1. Los id deben seguir existiendo y con el mismo nombre: main, luxText, brightnessText, statusText, connectButton, sendSwitch.
  2. El tipo de la View en el XML debe ser compatible con el tipo declarado en Java, o el cast revienta en tiempo de ejecución.

Por qué se conservan Button y Switch "nativos"

Material 3 ofrece widgets más lindos como com.google.android.material.materialswitch.MaterialSwitch. Pero el Java declara android.widget.Switch, y MaterialSwitch no hereda de android.widget.Switch (hereda de CompoundButton por otra rama). Si pusiéramos un MaterialSwitch en el XML, esta línea:

sendSwitch = findViewById(R.id.sendSwitch);  // ClassCastException 💥

fallaría con ClassCastException. Como la consigna era no tocar el backend, mantuvimos <Switch> y <Button> nativos.

El truco: estilar por tema, no por widget Aunque sean widgets "viejos", al estar bajo Theme.Material3 el sistema les aplica automáticamente el estilo Material: el <Button> sale relleno y con esquinas redondeadas, y el <Switch> usa colorPrimary al activarse. Conseguimos el look de Material sin cambiar la clase del widget. Esto es justo la idea de la p.36: el aspecto vive en los recursos/tema, no incrustado en cada elemento.
Variable JavaTipo declaradoEtiqueta XML usada
luxText / brightnessText / statusTextTextView<TextView>
connectButtonandroid.widget.Button<Button>
sendSwitchandroid.widget.Switch<Switch>
(contenedores)— no referenciados en Java —<MaterialCardView>, <LinearLayout> libres

4 · El sistema de color (Material 3)

Material Design define tokens de color con roles semánticos (no "azul", sino "color primario", "color de superficie"…). En vez de pintar cada View con un hexadecimal, asignás colores a roles y luego usás el rol. Esto es la versión Material de la p.36 de la cátedra.

Paso 1 — definir los colores · res/values/colors.xml

Primero los valores crudos. Elegimos un índigo apagado (sobrio) y declaramos también la variante oscura:

res/values/colors.xml xml
<!-- Paleta clara (Material 3) -->
<color name="primary">#4255A4</color>
<color name="on_primary">#FFFFFF</color>
<color name="primary_container">#DEE0FF</color>
<color name="on_primary_container">#00115B</color>
<color name="surface">#FFFFFF</color>
<!-- … y las versiones _dark para el modo oscuro -->

El convenio primary / on_primary es de Material: on_X es el color del texto/icono que va encima de X. Por eso el número grande de brillo (que va sobre primary_container) usa on_primary_container y siempre tiene contraste suficiente.

Paso 2 — asignar colores a roles · res/values/themes.xml

El tema conecta cada color crudo con su token de Material. Aquí es donde un hexadecimal pasa a ser "el color primario de la app":

res/values/themes.xml xml
<style name="Base.Theme.Cai_app"
       parent="Theme.Material3.DayNight.NoActionBar">
    <item name="colorPrimary">@color/primary</item>
    <item name="colorOnPrimary">@color/on_primary</item>
    <item name="colorPrimaryContainer">@color/primary_container</item>
    <item name="colorOnSurfaceVariant">@color/on_surface_variant</item>
    <!-- … -->
</style>

Fijate en la cadena de referencias PDF · p.36: el layout dirá ?attr/colorPrimary → el tema dice que eso es @color/primary → colors.xml dice que eso es #4255A4. Tres niveles de indirección, y cada uno se puede cambiar sin tocar los otros.

Paso 3 — usar el color: ?attr/ vs @color/

Diferencia clave que conviene dominar:

SintaxisQué haceCuándo usarla
@color/primaryApunta al hexadecimal fijo en colors.xml.Casi nunca directamente en el layout: ignora el tema.
?attr/colorPrimary"Preguntá al tema activo qué color juega este rol ahora". En modo oscuro devuelve otro valor.Siempre en el layout, para que cambie solo con claro/oscuro.

Por eso en activity_main.xml todos los colores son ?attr/... y no @color/...: así el mismo layout se ve bien en ambos modos sin duplicar nada.

Paso 4 — modo oscuro con un qualifier · res/values-night/

La p.34 menciona values-[qualifier]. El qualifier -night es la pieza mágica: Android elige automáticamente values-night/themes.xml cuando el sistema está en modo oscuro. Tiene el mismo nombre de estilo pero apunta a los colores _dark:

res/values-night/themes.xml xml · qualifier
<item name="colorPrimary">@color/primary_dark</item>
<item name="colorPrimaryContainer">@color/primary_container_dark</item>

No escribimos ni una línea de Java para esto: es puro mecanismo de recursos de la cátedra. El layout, que pide ?attr/colorPrimary, recibe un valor distinto según el sistema operativo.

5 · El layout · res/layout/activity_main.xml

Estructura general

El árbol de Views, simplificado, queda así (cada sangría es un ViewGroup que contiene al siguiente, el modelo de la p.28):

ConstraintLayout  (id=main)        ← raíz; recibe el padding de las barras del sistema
└─ LinearLayout vertical           ← columna centrada, ancho máx 480dp
   ├─ TextView   título
   ├─ TextView   subtítulo
   ├─ MaterialCardView              ← TARJETA DE LECTURA (color primaryContainer)
   │  └─ LinearLayout vertical
   │     ├─ LinearLayout (icono ☀ + "LUMINOSITÉ")
   │     ├─ TextView  id=brightnessText   "–– %"   (64sp)
   │     └─ TextView  id=luxText          "Lux : –"
   ├─ LinearLayout (icono ᛒ + TextView id=statusText)
   ├─ Button   id=connectButton           "Connecter"
   └─ MaterialCardView (borde)            ← FILA DEL SWITCH
      └─ LinearLayout horizontal
         ├─ TextView  "Envoyer la luminosité…"  (weight=1)
         └─ Switch   id=sendSwitch

Dos detalles de diseño que vale la pena entender:

  • El ConstraintLayout raíz mantiene el id=main porque MainActivity lo usa para aplicar el padding de las barras de sistema (modo edge-to-edge). No lo podíamos renombrar ni quitar.
  • El ancho máximo se logra con layout_width="0dp" + app:layout_constraintWidth_max="480dp" + anclajes a izquierda y derecha. En un teléfono ocupa todo; en una tablet se queda centrado y no se estira feo.

La tarjeta de lectura (el corazón visual)

Toda la jerarquía visual gira en torno al porcentaje. Lo metimos en una MaterialCardView con color de fondo colorPrimaryContainer, esquinas de 28dp y sin sombra (elevation 0 = más sobrio):

res/layout/activity_main.xml xml
<com.google.android.material.card.MaterialCardView
    android:layout_width="match_parent"
    android:layout_height="wrap_content"
    app:cardBackgroundColor="?attr/colorPrimaryContainer"
    app:cardCornerRadius="28dp"
    app:cardElevation="0dp">

    <LinearLayout android:orientation="vertical"
        android:padding="28dp">

        <!-- fila icono ☀ + etiqueta LUMINOSITÉ -->

        <TextView
            android:id="@+id/brightnessText"
            android:text="@string/placeholder_percent"
            android:textColor="?attr/colorOnPrimaryContainer"
            android:textSize="64sp"
            android:textStyle="bold" />

        <TextView android:id="@+id/luxText"
            android:text="@string/placeholder_lux"
            android:textColor="?attr/colorOnPrimaryContainer" />
    </LinearLayout>
</com.google.android.material.card.MaterialCardView>

Anatomía de una línea, para no perder detalle:

  • @+id/brightnessText — el + significa "creá este id en R.java". Como ya existía y Java lo usa, el nombre es obligatorio §3.
  • @string/placeholder_percent — el texto inicial sale de strings.xml, no cableado PDF · p.36. Java lo sobrescribe en cuanto llega un valor del sensor.
  • ?attr/colorOnPrimaryContainer — color por rol, sensible al modo oscuro §4.
  • 64sp — tamaño en sp (scale-independent pixels): respeta el tamaño de fuente del sistema. Para textos siempre sp; para márgenes/tamaños de caja, dp.

Fila de estado, botón y switch

Debajo de la tarjeta hay tres bloques. El de estado es un LinearLayout horizontal con un icono Bluetooth y el TextView de estado:

<LinearLayout android:orientation="horizontal"
    android:gravity="center_vertical">
    <ImageView android:src="@drawable/ic_bluetooth"
        app:tint="?attr/colorOnSurfaceVariant" />
    <TextView android:id="@+id/statusText"
        android:text="@string/status_disconnected" />
</LinearLayout>

El botón es full-width (layout_width="match_parent") y, como vimos en §3, sigue siendo un <Button> que el tema Material estila solo. La fila del switch usa una MaterialCardView con borde (strokeWidth) en lugar de fondo, para agruparlo visualmente sin agregar peso. El android:layout_weight="1" en el texto empuja el Switch al extremo derecho:

<TextView android:layout_width="0dp"
    android:layout_weight="1"
    android:text="@string/label_auto_send" />
<Switch android:id="@+id/sendSwitch"
    android:enabled="false" />
Por qué layout_weight En un LinearLayout, weight reparte el espacio sobrante. Darle peso 1 al texto (con ancho 0dp) hace que el texto ocupe todo lo que sobra y el switch quede pegado a la derecha. Es el patrón estándar "etiqueta a la izquierda, control a la derecha".

6 · Iconos vectoriales · res/drawable/

La p.35 lista drawable-[qualifier]/ como carpeta de "ficheros bitmap (PNG/JPEG) o XML que describen objetos dibujables". Usamos la segunda opción: vectores (VectorDrawable), que escalan sin pixelarse y pesan nada. Cada icono es un <path> con datos SVG:

res/drawable/ic_bluetooth.xml xml · vector
<vector android:width="20dp" android:height="20dp"
    android:viewportWidth="24" android:viewportHeight="24">
    <path android:fillColor="@android:color/white"
          android:pathData="M17.71,7.71L12,2h-1v7.59…" />
</vector>

El relleno se declara blanco, pero en el layout lo teñimos con app:tint="?attr/colorOnSurfaceVariant". Así el icono respeta el tema (claro/oscuro) sin tener un color hardcodeado. Es la misma idea de "color por rol" del §4 aplicada a un drawable.

Honestidad sobre una limitación El icono Bluetooth y su color son estáticos: no se ponen verdes al conectar, porque cambiar su tinte requeriría código en MainActivity y la consigna era no tocar el backend. El estado real igual se comunica por el statusText ("Connecté à…", "Déconnecté"). Si en el futuro se permite un cambio mínimo en Java, bastaría un setColorFilter sobre el ImageView para reflejar el estado.

7 · Strings y traducción al francés · res/values/strings.xml

La cátedra insiste en no cablear textos en el layout (p.32 usa android:text="@string/name"). Movimos todos los textos visibles a strings.xml. Esto cumple dos objetivos: limpieza y, sobre todo, traducción.

res/values/strings.xml xml
<string name="title_app">Luminosité adaptative</string>
<string name="label_brightness">Luminosité</string>
<string name="status_disconnected">Déconnecté</string>
<string name="action_connect">Connecter</string>
<string name="label_auto_send">Envoyer la luminosité automatiquement</string>
El camino correcto de localización (para la próxima) Lo ortodoxo en Android sería dejar el español en values/strings.xml (idioma por defecto) y crear values-fr/strings.xml para el francés — exactamente el mismo mecanismo de qualifier que values-night §4, pero con código de idioma. Acá, como el requisito es que toda la app esté en francés, simplemente pusimos el francés como texto base. Si algún día se quisiera multi-idioma, se añade values-es/ sin tocar el layout.

Los textos dinámicos viven en Java

Algunos textos no pueden estar en strings.xml porque se construyen en tiempo real (incluyen un valor o el nombre del dispositivo). Esos están en MainActivity y también se tradujeron — son literales, no lógica:

luxText.setText(String.format("Lux : %.0f", lux));
statusText.setText("Connexion...");
statusText.setText("Connecté à " + device.getName());
toast("Activez le Bluetooth");

Nota tipográfica: en francés se deja un espacio antes de : — por eso "Lux : %.0f" y no "Lux:".

8 · Cómo la UI se conecta con el sensor

El rediseño es solo "la cara"; conviene ver cómo se llena de datos, porque ahí entra la otra mitad del PDF: los capteurs.

El sensor de luz PDF · p.45, 55-57

La p.45 clasifica la luz (éclairage) como un capteur environnemental. La p.55-57 muestra el patrón exacto que usa esta app:

  • SensorManager + getDefaultSensor(Sensor.TYPE_LIGHT) para obtener el sensor.
  • Registrar el listener en onResume() y quitarlo en onPause() — la cátedra lo muestra textual en la p.56. Es clave para no gastar batería cuando la app no está visible.
  • onSensorChanged(SensorEvent) recibe los valores en event.values[] (p.57).
MainActivity.java java
public void onSensorChanged(SensorEvent event) {
    float lux = event.values[0];          // p.57: valores en values[]
    int pct = luxToPercent(lux);
    luxText.setText(String.format("Lux : %.0f", lux));   // ← actualiza la UI
    brightnessText.setText(pct + " %");             // ← el número grande
    // … si el switch está activo, envía por Bluetooth
}

O sea: el sensor escribe directamente en los dos TextView que rediseñamos. El rediseño no cambió esta tubería — solo cambió cómo se ven esos dos textos (tamaño, color, ubicación en la tarjeta). Esa separación limpia entre "datos" (Java/sensor) y "presentación" (XML/recursos) es precisamente lo que permite rediseñar sin romper nada.

  SENSOR DE LUZ ──► onSensorChanged() ──► setText() ──► TextView (XML rediseñado)
   (p.45,57)          (Java, intacto)                    (recursos, lo que tocamos)
        └──────────────── backend ────────────────┘   └──── frontend ────┘

9 · Para dominar el código (ejercicios)

Si querés tener control real sobre esto, probá estos cambios. Cada uno refuerza un concepto del PDF:

  1. Cambiá el color de marca. Editá solo #4255A4 en colors.xml y mirá cómo cambian la tarjeta y el botón a la vez. → entendés la indirección de la p.36.
  2. Rompé el modo oscuro a propósito. Cambiá un ?attr/colorOnPrimaryContainer por @color/on_primary_container (fijo) y observá cómo en modo oscuro el texto pierde contraste. → entendés ?attr/ vs @color/.
  3. Agregá una dimensión. Creá res/values/dimens.xml con <dimen name="gap">24dp</dimen> y usá @dimen/gap en los márgenes. → practica recursos de la p.34.
  4. Probá romper el contrato. Cambiá <Switch> por <com.google.android.material.materialswitch.MaterialSwitch> sin tocar Java y mirá el ClassCastException al abrir la app. → entendés §3 en carne propia (¡acordate de revertirlo!).
  5. Localizá de verdad. Movés el francés a values-fr/strings.xml y ponés español en values/; cambiá el idioma del emulador. → entendés los qualifiers de la p.34.
